OneRec：快手的端到端生成式推薦（OneRec Technical Report）

一句話：快手用一個「編碼器加解碼器」的生成模型，直接「寫出」要推薦給你的影片編號，取代傳統「召回 → 粗排 → 精排」的多階段漏斗。它還像訓練 ChatGPT 一樣，用強化學習和獎勵模型來調整推薦結果。

頁碼說明：PDF 共 39 頁。正文 p.1–25，參考文獻 p.26–28，附錄 p.29–39（貢獻者名單、A/B 測試實作細節、tokenizer 案例、符號表）。

背景：它想解決什麼問題

傳統的多階段串接（cascade）架構有三個問題（§1, p.3）：

  1. 算力被切碎：
    • 以快手為例，上線服務時超過 50% 的資源花在通訊和儲存，不是在計算（p.3）。
    • 排序模型在旗艦 GPU 上的利用率（MFU）訓練時只有 4.6%、推論時只有 11.2%；大型語言模型約 40%（p.3）。
  2. 目標互相衝突：
    • 快手有「數百個」來自使用者、創作者和平台生態的目標，在不同階段介入，互相拉扯（p.3）。
    • 不同階段的模型大小、結構不同，即使目標相同也會衝突，例如召回受限於排序，排序又受限於召回的結果（p.3）。
  3. 跟不上 AI 進展：多階段架構很難套用 scaling law、強化學習等大型語言模型的突破（p.3）。

核心做法

1. Tokenizer：把影片變成「語意 ID」（§2.1, p.5–7）

  • 影片數量是十億級而且一直增加，不可能每支影片都當成一個 token。
  • 做法：
    1. 用多模態模型（miniCPM-V-8B）讀影片的標題、標籤、語音轉文字、畫面文字、封面和 5 張畫面（p.6）。
    2. 再用「協同訊號」對齊：常被同一批人喜歡的影片，表示要接近（p.6）。
    3. 用 RQ-Kmeans 把每支影片編成 3 層、由粗到細的語意 ID，例如 (3, 4, 1)（p.6–7）。
  • 好處：相似影片共享前綴，新影片也能被表示（p.5）。

2. 編碼器：理解你（§2.2, p.7–9）

四條路徑：

  • 靜態：使用者 ID、年齡、性別。
  • 短期：最近 20 次互動。
  • 正回饋：256 個高互動影片。
  • 終生：最多 10 萬支看過的影片，先分群壓縮（p.8–9）。

3. 解碼器：一個 token 一個 token 生成推薦影片（§2.3, p.9–10）

  • 和語言模型一樣做「下一個 token 預測」，一次生成一支影片的 3 個語意 ID。
  • 用混合專家（MoE）擴大模型容量（p.10）。

4. 獎勵系統與強化學習（§2.4, p.10–13）

  • 偏好獎勵（P-Score）（p.10–11）：
    • 傳統做法是把點擊、按讚、留言、觀看時間等預測值用人工調的權重加總。這很難調，也不夠個人化。
    • OneRec 改用一個神經網路學出「個人化的綜合分數」。
  • ECPO：改良版的 GRPO 強化學習演算法，讓訓練更穩定（p.11–12）。
  • 格式獎勵（p.12–13）：
    • 加入強化學習後，超過一半生成的 ID 對不到真實影片，作者稱為「擠壓效應」（p.21）。
    • 加入格式獎勵後，合法率回升到約 95%（p.21）。
  • 產業獎勵（p.13, p.22）：
    • 平台的其他需求（生態、商業化、冷啟動、長尾影片）直接寫進獎勵裡。
    • 例子：壓低「搬運剪輯類內容農場」影片的獎勵，讓這類影片的曝光降低 9.59%，核心指標維持穩定（p.22）。

5. 訓練（§3, p.13–15）

  • 預訓練：每天約 180 億筆樣本（540 億 token）；0.935B 模型大約訓練 1000 億筆樣本後收斂（p.14）。
  • 後訓練：用即時資料流線上訓練。保留播放時長較高的那一半曝光做拒絕採樣微調，並抽 1% 使用者做強化學習（p.15）。

關鍵數字與結果（皆為作者報告）

線上 A/B 測試（§4.5, p.23–24, Table 12）

  • 測試範圍：快手和快手極速版主要場景（日活 4 億）、5% 流量、為期一週（p.23）。
  • OneRec 加上獎勵模型篩選：
    • App 停留時間 +0.54%／+1.24%（p.23, Table 12）。
    • 7 日留存（LT7）+0.05%／+0.08%（p.23）。
    • 按讚、追蹤、留言等也都上升。
  • 判讀門檻：在快手，停留時間 +0.1%、LT7 +0.01% 就算統計顯著（p.23）。
  • 本地生活服務場景：GMV +21.01%、訂單 +17.89%（p.23）。之後該場景已 100% 改用 OneRec（p.24）。

部署範圍

  • 已部署到約 25% 的 QPS（p.1, p.4, p.23）。
  • ⚠️ 附錄 B（p.30）說明：OneRec 升級的是系統原本在高峰時段「改用快取結果」的那部分流量。實驗組佔 5% 流量，OneRec 處理實驗組裡 25% 的快取流量。和「完全即時」的對照組相比仍然較好（Table 13, p.30–31）。

效率

  • MFU：訓練 23.7%、推論 28.8%，分別是原排序模型的 5.2 倍和 2.6 倍（p.4）。
  • 營運成本只有傳統管線的 10.6%（p.1, p.4）。

Scaling

  • 模型從 0.015B 到 2.633B 參數，越大損失越低（Table 1, p.15；p.16）。
  • 推論時生成的候選數（Pass@K）從 8 增加到 512，指標持續提升（Table 4, p.18）。

⚠️ 代理指標的反例（教學重點）

  • 只用「看完率（vtr）」當強化學習獎勵時，觀看時間和停留時間上升，但「觀看影片數（Video View）」明顯下降（Table 6, p.20）。作者明說，這「不一定代表高品質推薦」（p.19）。
  • 作者也承認，獎勵定義不夠好，導致輕微的 reward hacking（p.21）。
  • 改用 P-Score 當獎勵後，停留時間、觀看時間和觀看影片數才一起上升（Table 10, p.21）。

限制與注意事項（含作者自述，§5, p.25）

  • 作者自述：推理能力還不明顯；還沒整合 LLM 和 VLM；獎勵系統設計「還很初步」（p.25）。
  • 還沒有涵蓋快手全部流量（p.25）。
  • 這是技術報告，不是同儕審查論文；所有數字都是快手自己報告的。
  • 優化目標仍然以停留時間、觀看時間、留存為主（p.23），也就是互動和黏著度指標。

與其他來源的關係

  • 挑戰 YouTube 2016 和 X 開源 README 的多階段漏斗：OneRec 認為串接架構會造成算力碎片化和目標衝突（p.3）。見 多階段漏斗 vs. 端到端生成：推薦系統的架構之爭。
  • 和 HSTU 同一路線 HSTU 2024：都是生成式、都觀察到 scaling law。OneRec 更進一步，把召回到排序整個換成一個模型，並加入強化學習。
  • 優化目標：
    • X 用寫在程式碼裡的權重加總多種行為預測（X 開源 README, #Scoring and Ranking）。
    • OneRec 認為人工權重難調、不個人化，改用學出來的 P-Score（p.10）。
    • 見 優化目標。
  • embedding 的第四種解法：語意 ID（共享前綴、固定詞彙）。前三種是截斷詞彙表、無碰撞雜湊、多雜湊函數，見 嵌入向量。
  • 線上訓練：後訓練使用即時資料流（p.15），和 Monolith 2022 的即時更新方向一致。
